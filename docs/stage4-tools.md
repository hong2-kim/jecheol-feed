## 시험 (비발행)

- `news.py`: 구글 뉴스 검색 5건, 구글 뉴스 주소 3개를 원래 주소로(5.4초), 본문 6곳(이투데이, 한국경제, 뉴시스, 금강일보, 연합뉴스, 더바이어). 연합뉴스처럼 WebFetch 가 막힌 곳도 본문이 나온다.
- `photos.py`: `commons` 출력이 예전 파일과 글자까지 같다. 같은 검색 두 번째는 0.14초(저장된 결과). 관광공사 가짜 응답(주소 없는 항목, 한 장짜리)도 멈추지 않는다. `sheet commons` 10장 처음 10.4초(위키미디어 1초 간격을 지킴), 다시 0.23초. 관광공사 사진 16장: 한 장씩 2.2초 → 함께 받기와 모아 보기까지 0.7초, 다시 0.25초. 깨진 사진 1장은 "못 받음"으로 표시하고 계속.
- `web.py` 가짜 응답 시험: Retry-After 3초, Retry-After 날짜(4.7초), 120초는 기다리지 않음, 헤더 없으면 2·4·8초 뒤 그만, 503 도 같음, 404 는 다시 안 함, 연결 끊김 1초 뒤 다시, 같은 곳 두 번째 요청 1초 간격.
- `setup_env.py`: 빈 가상환경에서 7.3초 만에 Pillow·numpy 설치, 그 파이썬으로 `build.py` 검사 정상. 두 번째는 바로 "준비돼 있어요". 클라우드는 Python 3.11 이라 3.12 에서만 되는 f-string 꼴이 없는지 봤다(없음).
- 회귀: 설계도 38개 렌더링이 main 과 같다(같은 사진 저장본으로). 규칙 문장은 main 의 1,726개 가운데 1,725개 그대로, 바뀐 1개는 `pip install pillow` 괄호. `today_rules.py` 결과 같음.

## 예상 절감 (10-19 실행 기준, 병합하고 다음 실행부터)

- 턴: 위 표의 약 25턴(114턴의 약 22%) 가운데 대부분. 도구를 만드는 3턴, 패키지 8턴은 거의 없어지고, 모아 보기 기다림 10턴은 1~2턴으로, 429·오류 4턴은 1턴 안팎으로 준다고 본다.
- 시간: 패키지 약 2분 + 모아 보기 약 5분 → 약 7분(22.5분의 약 30%). 클라우드(해외)에서는 사진 받는 시간이 이 컴퓨터보다 길어서 함께 받기 효과가 더 크다.

- 숫자는 한 번의 실행 기록으로 어림한 것이다. 병합 뒤 같은 요일 실행의 턴 수와 시간으로 확인한다.
